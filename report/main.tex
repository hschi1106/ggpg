\begin{abstract}
Gene-pool Optimal Mixing Evolutionary Algorithms for genetic programming (\gpgomea) can find compact symbolic-regression models, but their variation operator repeatedly evaluates small, sequentially dependent candidate changes.
This execution pattern underutilizes a GPU when each candidate is dispatched independently.
We design two CUDA backends for \gpgomea: a control-flow exact backend that preserves immediate Gene-pool Optimal Mixing accept--reject decisions, and a batched backend that evaluates multiple candidate programs per launch while delaying some population updates.
Expressions are serialized into postfix token programs and evaluated by a sample-parallel stack-machine kernel.
The implementation further uses single-precision device data, reusable pinned and device buffers, CUDA Graph replay for exact evaluation, and host-side subtree and serialization caches.
Across a throughput stress-test matrix containing \AccelerationRuns{} runs, exact GPU evaluation achieves a median \ExactMedianSpeedup$\times$ wall-clock speedup over the original CPU path, while the best batched configuration reaches \BestBatchMedianSpeedup$\times$.
On a separate 100-generation study, batched evaluation changes the evolutionary trajectory and therefore must be treated as an approximate algorithmic variant rather than a transparent implementation optimization.
These results characterize the workload scale at which exact GPU evaluation becomes useful and the quality--throughput tradeoff introduced by batching.
A bounded selected Paper-G rerun is included for context; the full reference-paper experiment matrix was not rerun.
\end{abstract}

\section{Introduction}

Symbolic regression searches for an analytic expression that explains observed input--output data.
Genetic programming (GP) is a natural approach because it directly evolves expression trees, but conventional variation often disrupts useful subexpressions and can produce unnecessarily large models~\cite{koza1992genetic,polirefieldguide}.
\gpgomea addresses this problem with linkage learning and Gene-pool Optimal Mixing (GOM), which modifies selected locations while retaining a change only when it does not degrade fitness~\cite{virgolin2017scalable,virgolin2021improving}.
The resulting search is effective for small expressions, yet computationally demanding: a generation may contain many more fitness evaluations than the population size, and each accepted move changes the state used by later moves.

GP fitness evaluation is data parallel, making GPUs an attractive target~\cite{langdon2008simd}.
However, the natural unit of GOM work is often a single small candidate tree evaluated over a modest number of samples.
Launching one GPU kernel per candidate can cost more than evaluating that candidate on a CPU.
Combining candidates into larger launches improves utilization, but changes the sequential dependency structure that defines exact GOM.
The engineering question and the algorithmic question are therefore inseparable: how can \gpgomea expose enough parallel work for a GPU, and what search distortion is introduced when candidate decisions are batched?

This paper makes the following contributions:

\begin{itemize}
  \item We present a CUDA fitness-evaluation path that serializes pointer-rich expression trees into compact postfix programs and maps one program to a CUDA block, allowing threads in a warp to execute the same tree instructions over different samples.
  \item We distinguish a control-flow exact GPU backend from a delayed-commit batched backend, making the semantic cost of batching explicit.
  \item We describe and evaluate implementation techniques that reduce launch, transfer, allocation, and serialization overhead for both GPU paths.
  \item We measure acceleration across population size and data size, then separately study fitness evolution and batch-induced distortion over 100 generations.
\end{itemize}

\section{Background and Related Work}

\subsection{GP-GOMEA}

\gpgomea represents each individual with a fixed full-tree template.
Inactive nodes allow the expressed model to have a smaller shape, while the fixed genotype gives every tree location a stable index~\cite{virgolin2021improving}.
The population is used to learn a linkage model, represented as a Family of Subsets (FOS), whose subsets identify locations that should be mixed together~\cite{thierens2013optimal,virgolin2017scalable}.

For each parent, GOM visits FOS subsets in randomized order.
It copies the corresponding operators from a donor, evaluates the modified individual, and immediately accepts a non-worsening move or restores the previous operators.
This immediate accept--reject behavior is important: the candidate generated for the next FOS subset depends on every earlier decision.
The original CPU implementation evaluates each meaningful candidate as soon as it is created.

The reference symbolic-regression study improves \gpgomea for small expressions and evaluates fixed-population and Interleaved Multistart Scheme settings over multiple datasets~\cite{virgolin2021improving}.
Our work does not propose a new linkage model.
It targets the computational bottleneck created by repeated candidate fitness evaluation.

\subsection{GPU Genetic Programming}

Prior GPU GP systems exploit the fact that many fitness cases can be evaluated independently, commonly using interpreters or linearized programs on the device~\cite{langdon2008simd}.
The challenge for \gpgomea is finer-grained than a conventional generational GP evaluation: meaningful candidates appear throughout GOM, candidate program shapes differ, and exact decisions are sequential.
Our design follows the established idea of device-side program interpretation, but adapts it to GOM's immediate and batched candidate-evaluation modes.

\section{GPU-Accelerated GP-GOMEA}

\subsection{Execution Backends}

The implementation exposes three backends:

\begin{description}
  \item[\cpuoriginal] The upstream CPU evaluation and GOM control flow.
  \item[\exactgpu] Immediate GOM decisions are preserved, but each meaningful candidate is evaluated on the GPU.
  \item[\batchgpu] Multiple candidates are collected, evaluated together, and committed after the batch-local decision phase.
\end{description}

\exactgpu is \emph{control-flow exact}: it preserves the timing and ordering of GOM decisions.
It is not bitwise identical to the CPU backend because device math and parallel reduction ordering differ from host evaluation, even though both paths store single-precision values.
Small numerical differences can change a tie or accept--reject decision.
\batchgpu additionally changes donor visibility and candidate state by delaying commits, so it is an approximate search algorithm even if its arithmetic were identical.

\subsection{Algorithms and Update Semantics}

Algorithms~\ref{alg:cpu-gom}--\ref{alg:batch-gom} make the semantic boundary between the three backends explicit.
\textsc{MixAndMutate} copies the operators selected by an FOS subset from a random donor and applies coefficient mutation, while retaining a rollback record.
A move is meaningful when at least one effectively changed node is active rather than an intron.
Nonmeaningful changes are retained without reevaluation because they do not change the expressed model.
\textsc{Finalize} applies the implementation's optional tournament-based forced-improvement fallback when no strictly improving move was found.

\begin{algorithm}[t]
\small
\DontPrintSemicolon
\KwIn{parent $x$, population $P$, FOS $\mathcal{F}$}
\KwOut{offspring $x'$}
$x' \leftarrow \operatorname{clone}(x)$; $f \leftarrow \operatorname{fitness}(x)$; $improved \leftarrow false$\;
\ForEach{$S \in \operatorname{shuffle}(\mathcal{F})$}{
  $d \leftarrow \operatorname{uniform}(P)$\;
  $(r, meaningful) \leftarrow \textsc{MixAndMutate}(x',d,S)$\;
  \If{$meaningful$}{
    $f' \leftarrow \textsc{CPUFitness}(x')$\;
    \eIf{$f' \leq f$}{
      discard $r$; $improved \leftarrow improved \lor (f' < f)$; $f \leftarrow f'$\;
    }{
      $\textsc{Rollback}(x',r,f)$\;
    }
  }
  \Else{discard $r$}
}
\Return $\textsc{Finalize}(x',P,improved)$\;
\caption{Original sequential CPU GOM for one parent. Every meaningful move is decided immediately.}
\label{alg:cpu-gom}
\end{algorithm}

\subsection{Postfix Program Representation}

CUDA kernels do not receive C++ \texttt{Node} or \texttt{Op} pointers.
Each active expression is serialized on the host into a postfix sequence of \texttt{GpuToken} records.
A token contains an opcode, an optional feature index, and an optional constant.
The function set includes addition, subtraction, multiplication, and an explicit analytic quotient,
\begin{equation}
  \aq(a,b) = \frac{a}{\sqrt{1+b^2}},
\end{equation}
matching the operator used by the reference paper without changing the semantics of the upstream division operator~\cite{ni2013analytic}.

The batched representation stores token programs in a fixed-stride padded buffer and stores their active lengths separately.
The device kernel interprets one program per CUDA block and distributes fitness cases across the block's threads.
This mapping is central to handling tree-induced warp divergence.
All threads in a warp execute the same postfix instruction sequence for one expression, but on different rows of the dataset.
Programs with different shapes are assigned to different blocks rather than different lanes of the same warp.
Data-dependent exceptional cases can still diverge, but structural tree divergence is kept out of the warp.

\subsection{Exact GPU Evaluation}

Algorithm~\ref{alg:exact-gom} differs from original GOM in Algorithm~\ref{alg:cpu-gom} only at the meaningful-candidate fitness-evaluation boundary.
The exact backend serializes and evaluates each meaningful GOM candidate immediately.
This preserves GOM's update visibility, but the workload is vulnerable to kernel-launch and synchronization overhead.
To reduce that overhead, the implementation captures the single-program copy, reset, kernel, and result-copy sequence in a CUDA Graph and replays the graph for subsequent candidates~\cite{nvidiacuda}.
Pinned host buffers allow the graph to use asynchronous transfers, and device allocations grow by capacity rather than being recreated for each expression length.

\subsection{Batched GPU Evaluation}

Algorithm~\ref{alg:batch-gom} instead advances a population batch through each FOS step before committing its completed offspring to the donor population.
The batched backend collects candidates from a population batch, serializes them into a shared token buffer, evaluates them in one grid, and then applies accept--reject decisions.
The batch size controls the number of simultaneously evaluated programs.
Larger batches amortize launch and synchronization costs and expose more blocks to the GPU.
They also increase the delay before accepted changes become visible.
Consequently, batch size is both a performance parameter and a search hyperparameter.
The requested GOM batch size is an upper bound; the actual GOM launch size can be smaller when fewer meaningful candidates are available.
Reported actual GOM batch sizes exclude the one initial population-evaluation launch.

\subsection{Engineering Optimizations}

Several optimizations are shared by the GPU backends:

\begin{itemize}
  \item Numeric arrays use single precision. This reduces memory traffic. It also enables native floating-point atomics.
  \item Host token, length, and result buffers are pinned and reused; device program and reduction buffers are capacity-managed.
  \item Exact evaluation replays a CUDA Graph instead of issuing the same sequence of API calls for every candidate.
  \item Serialization vectors reserve capacity and are reused across candidates.
  \item The batched GOM path caches population subtree vectors and updates only entries whose individuals are replaced.
  \item The sample dimension uses multiple blocks when necessary, increasing available parallel work for larger datasets.
\end{itemize}

A persistent-kernel design was also evaluated during development, but it performed worse for this workload because queue management and synchronization overhead outweighed the saved launches.
It was not retained in the final implementation.

\section{Experimental Methodology}

\subsection{Research Questions}

We evaluate four questions:

\begin{description}
  \item[RQ1.] At what data and population sizes does exact GPU evaluation become faster than the original CPU path?
  \item[RQ2.] How does batch size affect wall-clock acceleration and candidate-evaluation throughput?
  \item[RQ3.] How much does delayed-commit batching change fitness evolution and final model quality?
  \item[RQ4.] Which implementation bottlenecks and optimization techniques explain the observed behavior?
\end{description}

\subsection{Hardware and Software}

Experiments were run on an AMD Ryzen 9 7950X CPU with 16 physical cores and 64\,MiB of L3 cache, 61\,GiB of system memory, and two NVIDIA GeForce RTX 4090 GPUs with 24\,GiB of memory each.
GPU timing runs use at most one process per physical GPU.
CPU acceleration baselines are run sequentially to avoid contention.
The CPU baseline uses the release CPU build, and GPU backends use the release CUDA build from the same source tree.
CUDA code is generated for compute capability 8.9, matching the RTX 4090 devices.

\subsection{Metrics and Statistical Analysis}

For a paired CPU and GPU run, wall-clock speedup is
\begin{equation}
  S_{\mathrm{wall}} = \frac{t_{\mathrm{CPU}}}{t_{\mathrm{GPU}}},
\end{equation}
and throughput ratio is the corresponding ratio of candidate evaluations per second.
We pair runs by dataset, seed, row scale, tree height, and population size.
Because batch search may evaluate a different number of candidates, wall-clock speedup and throughput ratio are reported separately.
Numerical divergence can also change the candidate sequence of \exactgpu, so wall-clock speedup is an end-to-end search measurement rather than a fixed-work kernel microbenchmark.

Fitness distortion is measured relative to \exactgpu under the same generation budget:
\begin{equation}
  R_{\mathrm{test}}(b) =
  \frac{\mathrm{NMSE}_{\mathrm{test}}(\text{batch size } b)}
       {\mathrm{NMSE}_{\mathrm{test}}(\text{exact GPU})}.
\end{equation}
A ratio below one favors batching.
We report medians and interquartile ranges, paired win/tie/loss counts, bootstrap confidence intervals for medians, and Wilcoxon signed-rank tests with Holm correction.
With five seeds, statistical results are interpreted as evidence about this implementation rather than a definitive ranking of symbolic-regression algorithms.
Nsight Systems is used on a representative Wine white row-scale-32, population-4096 case to distinguish launch-bound and kernel-bound behavior; profiling runs are not included in the timing summaries.

\subsection{Reference-Paper Comparison}

The original Paper-G fixed-population results are included as an external reference scale~\cite{virgolin2021improving}.
We rerun a selected four-dataset subset with height 4, population size 1000, linearly scaled MSE~\cite{keijzer2003linear}, no coefficient mutation, five seeds, and a 60\,s budget.
We did \emph{not} rerun the full paper matrix, which used 30 repetitions and a 1000\,s budget.
The selected rerun is therefore not a protocol-equivalent reproduction and is not used to claim superiority over the reference paper.

\subsection{RQ4: Bottlenecks and Optimization Effects}

Profiling and implementation experiments identify two distinct regimes.
The exact path is dominated by repeated host--device orchestration and synchronization for small candidate programs.
CUDA Graph replay, pinned reusable buffers, and single-precision reductions directly target this regime.
The batched path is less launch-bound and benefits more from enough independent programs, reduced serialization allocation, cached subtree vectors, and higher sample-level occupancy.
In a representative Wine white row-scale-32, population-4096 comparison against pre-optimization commit \texttt{851b0e9}, the cumulative changes improve exact-GPU wall time by \ExactOptimizationSpeedup$\times$ and batch-GPU wall time by \BatchOptimizationSpeedup$\times$ (Table~\ref{tab:optimization-ablation}).
Both binaries are built for compute capability 8.9.

\section{Discussion}

The results show that GPU acceleration is not a single yes-or-no property of GP fitness evaluation.
For small datasets and fine-grained exact GOM moves, CPU evaluation can remain competitive because it avoids launch and synchronization overhead.
As the number of fitness cases grows, exact GPU evaluation crosses over and becomes consistently useful.
Batching broadens the useful region by creating program-level parallelism, but changes the algorithm.

This distinction matters for scientific claims.
\exactgpu is suitable when preserving GOM's immediate decision structure is more important than bitwise numerical identity.
\batchgpu is suitable when throughput is the priority and batch size can be treated as a hyperparameter.
Reporting only evaluation throughput would obscure the fact that candidate counts and trajectories differ; reporting only final error would obscure the substantial computational benefit.
Both dimensions are necessary.

\section{Threats to Validity}

The throughput suite uses duplicated training rows to reveal scaling behavior.
These rows do not add information and cannot support accuracy claims.
The fitness study uses four datasets, three tree heights, and five seeds; broader conclusions require more datasets and repetitions.
Device math and parallel reduction ordering make \exactgpu a non-bitwise reproduction of CPU arithmetic.
The batched backend deliberately delays update visibility and is not semantically equivalent to exact GOM.

The full experiment matrix from the reference paper was not rerun.
The selected Paper-G comparison uses a shorter budget and fewer repetitions, and the main GPU fitness study uses a generation budget, MSE, and coefficient mutation.
The local harness also holds the prepared data split fixed across search seeds, which is another difference from a full repeated-split reproduction.
We therefore avoid direct algorithm-ranking claims against the original paper.
Finally, results are hardware-dependent: the balance between CPU scalar performance, GPU launch latency, memory bandwidth, and occupancy will differ on other systems.

\section{Conclusion}

We presented exact and batched GPU fitness-evaluation backends for \gpgomea symbolic regression.
The implementation linearizes expression trees into postfix programs, maps one program to a CUDA block to control warp divergence, and reduces orchestration and allocation overhead through CUDA Graph replay, reusable pinned buffers, single-precision evaluation, and host-side caches.
Exact GPU evaluation becomes advantageous when candidates contain enough sample work, while batched evaluation provides larger speedups by exposing program-level parallelism.
The batched method also changes fitness evolution, so its acceleration must be interpreted together with its search distortion.
Future work should evaluate the full reference-paper matrix, study adaptive batch sizing, and investigate mixed-precision acceptance checks that preserve more CPU decisions without sacrificing GPU throughput.
